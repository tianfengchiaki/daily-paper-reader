## 摘要
使用低秩自适应（LoRA）在终端用户数据上微调大型语言模型（LLM）可提供个性化体验并保护数据隐私，但在消费级硬件上面临严峻的内存限制。微调过程中的峰值内存通常超过设备限制，尤其是对于具有数十亿参数和长上下文训练数据的模型。本文介绍了一套互补技术，在不牺牲模型质量的前提下减少内存占用：（1）带即时反量化基础模型量化，（2）结合选择性激活缓存和磁盘卸载的内存高效检查点，（3）使用语义相关令牌子集的softmax近似，以及（4）logits掩码。在Llama-3.2 3B和Qwen-2.5 3B上的实验表明，峰值内存最多减少了26倍和28倍，从而能够在资源受限的设备上进行微调。

## Abstract
Fine-tuning of Large Language Models (LLMs) using Low-Rank Adaptation (LoRA) on an end-user's data offers personalized experiences while keeping data private, but faces severe memory constraints on consumer hardware. Peak memory during fine-tuning often exceeds device limits, especially for models with billions of parameters and long-context training data. This paper introduces a suite of complementary techniques to reduce memory footprint without sacrificing model quality: (1) base model quantization with on-the-fly dequantization, (2) memory-efficient checkpointing combining selective activation caching and disk offloading, (3) softmax approximation using semantically relevant token subsets, and (4) logits masking. Experiments on Llama-3.2 3B and Qwen-2.5 3B demonstrate up to $26\times$ and $28\times$ reduction in peak memory, enabling fine-tuning on resource-constrained devices.

# 边缘设备上LLM的LoRA微调峰值内存降低技术：详细总结

## 一、论文的核心问题与整体含义（研究动机和背景）

- **核心问题**：在资源受限的边缘设备（如智能手机、IoT设备）上对大型语言模型（LLM）进行参数高效微调（如LoRA）时，由于前向传播需要存储激活值，导致峰值内存远远超出设备限制，尤其当模型参数达数十亿、上下文长度较长时。
- **整体含义**：现有方案（如MobiLLM的服务器辅助、PocketLLM的零阶优化、MobileLLM的专用小模型）要么牺牲隐私和延迟，要么不兼容主流框架，且难以处理长上下文。本文旨在通过一套互补的、框架无关的优化技术，在不牺牲模型质量的前提下显著降低峰值内存，实现在边缘设备上的端到端LoRA微调。
- **关键瓶颈**：反向传播依赖前向激活值；输出层（LM head）的logits计算和softmax操作是内存消耗的最大来源，因为现代LLM词表规模可达12.8万～25.6万。

## 二、论文提出的方法论

### 核心思想
将四种正交技术组合为一个流水线，逐个击破内存瓶颈：参数存储、中间激活、输出logits（softmax）和训练序列中非必要token的计算。

### 关键技术细节

1. **基础模型量化与即时反量化（Base Model Quantization with On-the-fly Dequantization）**
   - 对冻结的基模型权重进行混合精度后训练量化：大部分线性层用INT4，输出头用INT8，输入嵌入用INT16。模型大小（如Llama-3.2 3B）从5.98 GB降至2.59 GB。
   - 为防止全精度矩阵运算时内存膨胀，量化的权重存储于片外存储（如SSD），在前向和反向传播需要时才动态反量化为FP32，使用后立即释放（Algorithm 1）。
   - 优点：大幅减少参数占用的内存；不依赖专用量化核。

2. **内存高效检查点（Checkpointing）**
   - 并非传统的仅重计算，而是结合选择性激活缓存和磁盘卸载。将网络分解为节点序列（嵌入层→n个解码器层→输出层），每个节点只缓存边界处的激活值，内部激活在反向传播时重计算；权重和缓存激活动态加载/卸载。
   - 关键策略：将输出层（LM head）设为最后一个节点，因为它是最大的内存瓶颈，且不需要重计算（前向已完成）。
   - Algorithm 2描述了精确流程：Stage I前向缓存激活（存储到芯片外），Stage II计算loss并保存输出节点梯度，Stage III反向传播时重计算中间激活并加载节点权重。
   - 效果：相较于仅量化，8K tokens下Llama-3.2 3B从53.07 GB降至12.21 GB。

3. **Softmax近似（Softmax Approximation）**
   - 核心直觉：预训练模型的词嵌入矩阵已经编码了语义相似性，且next-token概率向量高度稀疏。微调时，大部分词汇与当前语义无关。
   - 方法：预先计算词嵌入间的余弦相似度矩阵，对每个目标token保存其最相似的Top-K个token索引。微调时，对于一个输入序列，取所有目标token的Top-K索引的并集作为缩减后的“有效词表” $\mathcal{J}$。仅加载此子集的嵌入权重，计算缩减后的logits和概率（图1b）。
   - 存储开销：存储预先计算的Top-K索引表，例如对于Llama-3.2 3B（词表128256），$k=500$时需约245 MB片外存储，可重复用于所有微调任务。
   - 实验显示，$k=500$在XSum数据集上即可达到与完整softmax相近的收敛效果。

4. **Logits掩码（Logits Masking）**
   - 在指令微调中，通常对非训练token进行loss掩码（设为-100）。本文提出进一步：完全跳过这些token的logits计算，仅在LM head阶段处理训练token。这相当于缩短了LM head处理的有效序列长度。
   - 限制：仅适用于存在大量非训练token的任务（如摘要、QA），且无法直接用于batch大于1的情况（需对batch内不同序列进行循环）。
   - 与softmax近似组合效果更佳。

### 算法流程说明
- 总流程：量化基模型 + 动态反量化 → 检查点（缓存+卸载） → 以缩减词表执行softmax → 仅对训练token计算logits。
- 反量化算法（Algorithm 1）：从片外加载量化权重 → 反量化为FP32 → 执行线性运算 → 使用后立即释放FP32权重。
- 检查点算法（Algorithm 2）：依次处理嵌入层、解码器层（前向无梯度），将前一层激活缓存；最后处理输出层（带梯度）；反向传播时从后往前重加载节点和缓存激活，执行带梯度的前向和反向。

6. **各技术正交可叠加**：检查点+softmax近似+logits掩码效果强于任意两项组合。

## 七、优点

- **系统性、模块化**：四种技术覆盖了参数、激活、输出层、无贡献token四个维度的内存瓶颈，且彼此正交，易于集成到现有Pipeline（如PyTorch）。
- **实用导向**：所有方法均避免复杂硬件依赖，使用标准FP32/INT4核；软近似仅需预计算一次词向量相似度表，存储开销小。
- **彻底消融**：论文通过大量profiling清晰地展示了每个步骤的贡献，并揭示了瓶颈转移现象（从输出层到解码层）。
- **公平评估**：评估指标使用完整softmax计算的损失或下游任务指标，非近似loss，避免方法偏差。
- **边缘实测**：从理论Profiling到真实手机测量，验证了实用可行性。

## 八、不足与局限

- **软近似仅限文本**：提出的基于语义相似性的软近似依赖于语言模型的词嵌入，无法直接推广到多模态、语音、检索增强等非标准输出空间。附录中也提到该局限。
- **Logits掩码任务依赖**：内存节省仅在大多数token非训练（如指令微调）时显著；若几乎所有token都需训练（如续写），收益接近于零。
- **边缘设备测量代表性有限**：只测试了一款2025年顶级智能手机；不同SoC、内存架构、驱动栈可能导致不同结果，不能作为普遍基准。
- **评估任务较窄**：主要文本摘要和问答，未涉及长文本生成、代码、多轮对话等场景；GSM8K/MATH虽为数学推理，但指令格式类似；未验证多任务联合微调。
- **未与现有的极端压缩方法充分比较**：例如未与QLoRA（4-bit加载+双量化）、LoRA-FA（激活近似）等直接对比峰值内存（仅提及正交性）。
- **延迟成本**：检查点带来重计算，softmax近似和logits掩码减少了计算，但总体延迟仍随上下文长度显著增加（Table 8：2048 tokens延迟升至802.49%），在交互式应用中可能不被接受。
